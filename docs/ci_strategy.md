# CI strategy

**Question this answers:** how do I know a pull request is safe to merge, and how do I keep that check fast and cheap?

## What runs on each pull request

Workflow: [`.github/workflows/ci.yml`](../.github/workflows/ci.yml). It runs on every pull request to `main` (and can be started manually once the file is on `main`).

```text
checkout -> Python 3.11 -> install pinned tools -> dbt deps
  -> sqlfluff lint models tests -> load CI sample -> dbt build
```

- Tool versions are pinned (`dbt-core 1.10.22`, `dbt-duckdb 1.10.0`, `sqlfluff 4.1.0`) to match local development.
- Cheap checks run first. If a step fails, the following steps are skipped.
- `dbt build` runs seeds, models, snapshots and tests in DAG order. If a test fails, downstream models are skipped.
- CI uses its own profile, [`ci/profiles.yml`](../dbt-project/ci/profiles.yml): a new DuckDB file on each run, no credentials.

## CI data: a small sample

The full CSV seeds are about 2.4 GB, exist only on my machine and are not in Git. A runner starts empty, so CI uses a committed sample in `dbt-project/ci/seeds/` (about 750 KB).

`scripts/make_ci_sample.sql` picks 1,000 orders in a reproducible way, then filters related tables by their keys, so relationship tests stay valid.

**What the sample can miss:**

- Rare bad values that exist in the full data but not in the sample.
- Performance problems, such as an expensive join that is still fast on 1,000 orders.
- Behaviour that depends on history, such as incremental merges: every CI run starts from an empty database, so incremental models are always built from scratch.

A green check means "the code builds and passes tests on the sample", not "the production data is correct".

## State, defer and clone: not used in this CI

My "production" is a DuckDB file on my laptop. A GitHub runner cannot reach it, so there is nothing to compare with, defer to or clone from. Building everything on the sample is simple and takes under a minute.

I practised these locally:

| Feature | Purpose |
|---|---|
| `state:modified+` | Select what changed compared with a baseline manifest, plus everything downstream |
| `--defer` | Read unselected, unbuilt parents from the production location (only referred node, not with their upstream) |
| `dbt clone` | Create objects in the target schema from production without running model SQL |

On DuckDB, `dbt clone` created a view that selects from the source table, not a copy. My untested assumption is that such a view cannot serve as the target of an incremental merge.

**With a shared warehouse (design only, not built here):**

1. After a merge to `main`, a job publishes the production `manifest.json`.
2. The PR job downloads it as the baseline.
3. Modified incremental models that already exist in production are cloned into the PR schema.
4. `dbt build -s state:modified+ --defer --state <baseline>` builds only what changed and what depends on it.

## Retry and `--empty`

- `dbt retry` reruns the nodes that failed or were skipped, based on `target/run_results.json`. I tested it locally: after one failed and one passed test, retry ran only the failed one. It is not part of CI, because each runner is discarded with its results.
- `--empty` builds with zero input rows to check that the SQL runs. Data tests then pass without proving anything. **Not tested yet in this project.**

## Known limits and next steps

- The CI check is not yet configured as required for merging.
- No state comparison or baseline publishing, for the reason above.
- The sample is regenerated by hand when the source data or schema changes.
