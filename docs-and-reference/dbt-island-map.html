Materialization & incremental

2.5–3

Choose cost and runtime against freshness, model by model.

  • view · table · ephemeral · incremental
  • is_incremental() + unique_key
  • Strategies: merge, delete+insert, append, insert_overwrite, microbatch
  • Lookback window for late data; on_schema_change
  • --full-refresh; --empty (is my SQL valid?) vs --sample (is the result sensible?)
Watch out

Incremental is still a physical table. A 3-day lookback for 2-day-late events leaves 1 day of buffer, and unique_key + merge updates late rows instead of duplicating them.

Proof

fact_order incremental with 3-day lookback. audit_helper shows 100% match against a full refresh. Before/after runtime table in docs/incremental_proof.md.

Jinja & macros

2 / 5

Stop copy-pasting SQL. Turn a repeated pattern into one piece.

  • {{ }} prints, {% %} controls
  • ref, source, config, var, target
  • Macros with arguments
  • A custom generic test is a macro: {% test name(model, column_name) %}
  • target/compiled = the SELECT; target/run = the full statement sent
Watch out

Do not study this as its own topic. Learn it by writing the custom generic tests in M1: one exercise, two skills. A warehouse error means look in run/, not compiled/.

Proof

assert_non_negative and assert_sum_matches used on 2+ models. You can say why this is a macro and not a singular test.

Testing

2.5 / 5

Check the logic before merge and the data before anyone reads it.

  • Order of defence: freshness → unit → data tests
  • Generic, singular and custom generic tests
  • Unit tests: given / expect for branching logic (CASE, window, date math)
  • Configs: severity, warn_if / error_if, where, store_failures
  • Source freshness: loaded_at_field, warn_after, error_after
  • In dbt build: a fail skips downstream, a warn does not
Watch out

40 failing rows with warn_if: ">0" and error_if: ">100" is a WARN and downstream still builds. 150 rows is a FAIL and downstream is skipped. No unit tests for select, rename or pass-through.

Proof

2 unit tests on int_order_financials (discount > subtotal, null fee), 2 custom generic tests, freshness in _sources.yml, where on a big fact, one deliberate red run, docs/testing_strategy.md.

CI/CD & state

1–1.5

Check every PR automatically without rebuilding everything.

  • manifest.json from main is the comparison state
  • state:modified = changed nodes only; state:modified+ adds downstream
  • --defer: unbuilt upstream ref() points at prod
  • dbt clone: copy prod objects into your schema
  • dbt retry resumes from the failed node
  • GitHub Actions, schema per PR (pr_<n>), SQLFluff, --empty dry run
Watch out

Defer applies to upstream, not downstream. Pick clone when the object must physically exist in your schema: incremental models, or a BI tool pointing at dev.

Proof

ci.yml: lint → build --select state:modified+ --defer --empty → real build into pr_<n>. A PR that goes red on a failing test, then green. Screenshot it.

Governance

1 / 5

Give consumers a promise the shape will not change silently.

  • Contracts (enforced): shape is checked before data exists
  • Constraints on columns
  • Versions + deprecation_date; consumers move with ref('m', v=2)
  • Access: private / protected / public; groups
  • Exposures: document consumers (dashboards, apps, ML); build and enforce nothing
Watch out

Renaming a column used by three teams in one go forces all of them to change together. Version it instead. A contract fails the build; a test checks data after it exists.

Proof

Contract and constraints on fact_order and fact_order_item. fact_order v2 with v1 deprecated. Exposures for the Streamlit app and text-to-SQL. The build fails if a column type changes without a version bump.
